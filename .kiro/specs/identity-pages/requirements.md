# Requirements Document

## Introduction

This specification defines the public-facing identity pages for the Portal platform: Registration, Confirm Account, Forgot Password, and Reset Password. These pages form the entry point for the self-service onboarding flow where new users can register, select a subscription plan, confirm their email, and proceed to Stripe checkout. The pages follow the 3 Inventors Identity Page Design Guide (frosted glass cards, particle background, top bar, responsive layout) and coexist with the existing invitation-only registration flow which remains intact for adding users within a tenant.

## Glossary

- **Identity_Page_System**: The set of ASP.NET Core MVC controllers, views, and services responsible for rendering and processing the public identity pages (Registration, Confirm Account, Forgot Password, Reset Password).
- **Registration_Page**: The public-facing page where a new user provides their email, password, first name, last name, and selected subscription plan to create an account.
- **Confirm_Account_Page**: The page a user lands on after clicking the email verification link, displaying success or failure states.
- **Forgot_Password_Page**: The page where an existing user enters their email address to request a password reset link.
- **Reset_Password_Page**: The page where a user sets a new password using a token received via email.
- **Plan**: A subscription tier record (from `[dbo].[Plan]`) defining pricing, billing cycle, user limits, and available modules.
- **Email_Verification_Token**: A time-limited token generated by ASP.NET Core Identity to confirm a user's email address.
- **Password_Reset_Token**: A time-limited token generated by ASP.NET Core Identity to authorise a password change.
- **Identity_Layout**: The shared Razor layout implementing the 3 Inventors Identity Page Design Guide (top bar, particle background, frosted glass card, footer).
- **Particle_Background**: A full-screen canvas element rendering animated floating particles with connection lines and mouse interaction, as defined in the Identity Page Design Guide.

## Requirements

### Requirement 1: Shared Identity Layout

**User Story:** As a user, I want all identity pages to share a consistent visual design, so that I recognise the brand and feel confident in the platform's professionalism.

#### Acceptance Criteria

1. THE Identity_Page_System SHALL render all identity pages using the Identity_Layout with a top bar, content area, and footer as defined in the Identity Page Design Guide.
2. THE Identity_Layout SHALL display the product name "Portal" left-aligned within the top bar using a gradient background (`linear-gradient(180deg, #1A6BB8 0%, #0D5EA6 100%)`).
3. THE Identity_Layout SHALL render a frosted glass card (`backdrop-filter: blur(16px)`, `border-radius: 24px`, `max-width: 420px`) in the content area for all form content.
4. THE Identity_Layout SHALL render the Particle_Background canvas behind all content with `aria-hidden="true"` and `pointer-events: none`.
5. WHILE the user has `prefers-reduced-motion: reduce` enabled, THE Identity_Layout SHALL disable all animations including the Particle_Background and display a static gradient background instead.
6. THE Identity_Layout SHALL display a footer with the text "© {currentYear} Portal · 3 Inventors" centered below the content area, where {currentYear} is dynamically rendered from the server-side current year.
7. THE Identity_Layout SHALL include a shared favicon, Open Graph meta tags, and a page title in the format "{PageTitle} - Portal" on every identity page.
8. WHEN the viewport width is 900px or less, THE Identity_Layout SHALL hide the hero panel and display only the frosted glass card centered at full width (max 420px).
9. WHEN the viewport width exceeds 900px, THE Identity_Layout SHALL display a two-column grid (55% hero panel, 45% form card) with a hero panel on the left containing a product tagline and feature highlights, and the frosted glass card on the right.

### Requirement 2: Registration Page

**User Story:** As a new user, I want to register for the platform by providing my details and selecting a subscription plan, so that I can create my account and proceed to payment.

#### Acceptance Criteria

1. THE Registration_Page SHALL be publicly accessible at the route `/Account/Register` without requiring authentication.
2. THE Registration_Page SHALL display a form collecting: first name, last name, email address, password, and confirm password fields.
3. THE Registration_Page SHALL accept an optional `plan` query parameter (matching a Plan Slug) to pre-select the subscription plan.
4. WHEN the `plan` query parameter is provided and matches an active Plan Slug, THE Registration_Page SHALL display the selected plan name and monthly price on the card.
5. WHEN the `plan` query parameter is missing or invalid, THE Registration_Page SHALL display a plan selection section showing all active plans with their names and prices ordered by DisplayOrder.
6. WHEN the user submits the registration form with valid data, THE Identity_Page_System SHALL create a new ASP.NET Core Identity user with `EmailConfirmed` set to false.
7. WHEN the user submits the registration form with valid data, THE Identity_Page_System SHALL generate an Email_Verification_Token and send a confirmation email to the provided address.
8. WHEN the user submits the registration form with valid data, THE Identity_Page_System SHALL store the selected Plan Id in a pending registration record for use after email confirmation.
9. WHEN the user submits the registration form with valid data, THE Registration_Page SHALL redirect to a "check your email" confirmation view.
10. IF the email address is already registered, THEN THE Identity_Page_System SHALL display a validation error stating the email is already in use.
11. IF the password does not meet the policy (minimum 8 characters, one uppercase, one digit, one special character), THEN THE Identity_Page_System SHALL display specific validation errors for each unmet criterion.
12. IF the first name or last name is empty or exceeds 100 characters, THEN THE Identity_Page_System SHALL display a validation error for the missing or oversized field.
13. THE Registration_Page SHALL display a link to the Login page for users who already have an account.
14. THE Registration_Page SHALL not assign the user to any Business or grant any module permissions at registration time.
15. IF the password and confirm password fields do not match, THEN THE Identity_Page_System SHALL display a validation error stating the passwords must match.
16. IF no plan is selected when the user submits the form, THEN THE Identity_Page_System SHALL display a validation error requiring a plan selection.
17. IF the email address is not a well-formed email format, THEN THE Identity_Page_System SHALL display a validation error indicating a valid email address is required.

### Requirement 3: Confirm Account Page

**User Story:** As a newly registered user, I want to confirm my email address by clicking the verification link, so that my account is activated and I can proceed to payment.

#### Acceptance Criteria

1. THE Confirm_Account_Page SHALL be publicly accessible at the route `/Account/ConfirmEmail` without requiring authentication.
2. WHEN the page is loaded with a valid `userId` and `token` parameter, THE Identity_Page_System SHALL verify the Email_Verification_Token using ASP.NET Core Identity.
3. WHEN the token is valid and email confirmation succeeds, THE Confirm_Account_Page SHALL display a success message and a call-to-action button that navigates the user to the Stripe checkout session for their selected plan.
4. IF the token is invalid or expired, THEN THE Confirm_Account_Page SHALL display an error message indicating that the verification link is invalid or has expired, and SHALL display a link to request a new verification email.
5. IF the `userId` parameter does not match an existing user, THEN THE Confirm_Account_Page SHALL display a generic error message without revealing whether the user exists.
6. WHEN email confirmation succeeds, THE Identity_Page_System SHALL set `EmailConfirmed` to true on the user record.
7. IF the `userId` or `token` query parameter is missing, THEN THE Confirm_Account_Page SHALL display a generic error message indicating the link is malformed.
8. IF the user's email is already confirmed when the page is loaded, THEN THE Confirm_Account_Page SHALL display a message indicating the account is already verified and SHALL display the call-to-action button to proceed to Stripe checkout.

### Requirement 4: Forgot Password Page

**User Story:** As an existing user who has forgotten my password, I want to request a password reset link, so that I can regain access to my account.

#### Acceptance Criteria

1. THE Forgot_Password_Page SHALL be publicly accessible at the route `/Account/ForgotPassword` without requiring authentication.
2. THE Forgot_Password_Page SHALL display a form collecting the user's email address with a maximum input length of 256 characters.
3. WHEN the user submits a valid email address that matches an existing confirmed account, THE Identity_Page_System SHALL generate a Password_Reset_Token with an expiration of 24 hours and send a reset link via email to that address.
4. WHEN the user submits the form (regardless of whether the email exists or the account is unconfirmed), THE Forgot_Password_Page SHALL redirect to a confirmation view stating "If an account exists with that email, a reset link has been sent."
5. THE Forgot_Password_Page SHALL not reveal whether an email address is registered in the system, including for unconfirmed accounts.
6. THE Forgot_Password_Page SHALL display a link back to the Login page.
7. IF the email field is empty or contains a value that is not a well-formed email address, THEN THE Identity_Page_System SHALL display a validation error indicating a valid email address is required.
8. IF the submitted email matches an existing account that has not been confirmed, THEN THE Identity_Page_System SHALL not send a reset link and SHALL redirect to the same confirmation view as a successful submission.

### Requirement 5: Reset Password Page

**User Story:** As a user who requested a password reset, I want to set a new password using the link I received, so that I can regain access to my account.

#### Acceptance Criteria

1. THE Reset_Password_Page SHALL be publicly accessible at the route `/Account/ResetPassword` without requiring authentication.
2. THE Reset_Password_Page SHALL display a form collecting: new password and confirm password fields.
3. WHEN the Reset_Password_Page is loaded, THE Identity_Page_System SHALL extract `userId` and `token` query parameters from the reset link URL and validate the token against ASP.NET Core Identity before displaying the form.
4. WHEN the user submits a valid new password and the token is valid, THE Identity_Page_System SHALL update the user's password using ASP.NET Core Identity.
5. WHEN the password reset succeeds, THE Reset_Password_Page SHALL display a success message with a link to the Login page.
6. IF the token is invalid or expired, THEN THE Reset_Password_Page SHALL display an error message explaining that the reset link is invalid or has expired, and SHALL not display the password form.
7. IF the new password does not meet the password policy (minimum 8 characters, at least one uppercase letter, at least one digit, at least one special character), THEN THE Identity_Page_System SHALL display specific validation errors for each unmet criterion.
8. IF the password and confirm password fields do not match, THEN THE Identity_Page_System SHALL display a validation error stating the passwords must match.
9. IF the `userId` or `token` query parameter is missing from the URL, THEN THE Reset_Password_Page SHALL display a generic error message indicating the reset link is invalid, without revealing whether the user exists.
10. IF the `userId` does not match an existing user, THEN THE Reset_Password_Page SHALL display a generic error message without revealing whether the user exists in the system.
11. THE Reset_Password_Page SHALL display a link to the Forgot Password page so the user can request a new reset link.

### Requirement 6: Coexistence with Invitation Flow

**User Story:** As a super admin, I want the existing invitation-only registration flow to remain fully functional, so that I can continue adding users to existing tenants.

#### Acceptance Criteria

1. THE Identity_Page_System SHALL preserve the existing `InvitationController` routes, actions, views, and service calls at `/Invitation/Register` without modification.
2. THE Identity_Page_System SHALL use a separate controller from the `InvitationController` to handle public self-registration at `/Account/Register`.
3. WHEN a user registers via the public Registration_Page, THE Identity_Page_System SHALL create the user record without a BusinessId and without any module permission assignments.
4. WHEN a user registers via the invitation flow, THE Identity_Page_System SHALL assign the user to the inviting Business, create the user-business association, and grant the module permissions specified in the invitation.
5. WHEN a user who previously registered via the public Registration_Page accepts a subsequent invitation, THE Identity_Page_System SHALL assign the existing user to the inviting Business and grant the invited module permissions without requiring re-registration.
6. THE Identity_Page_System SHALL store both invitation-registered and publicly-registered users in the same ASP.NET Core Identity user store (Membership database) using the shared `ApplicationUser` entity.

### Requirement 7: Form Accessibility and Validation

**User Story:** As a user with accessibility needs, I want all identity page forms to be fully accessible, so that I can complete registration and account management tasks using assistive technology.

#### Acceptance Criteria

1. THE Identity_Page_System SHALL associate every form input with a corresponding `<label>` element using the `for` attribute.
2. WHEN a form submission fails validation, THE Identity_Page_System SHALL display validation errors using elements with `role="alert"` so screen readers announce them automatically.
3. THE Identity_Page_System SHALL ensure all text meets a minimum contrast ratio of 4.5:1 for normal text and 3:1 for large text (WCAG AA) against the frosted glass card background.
4. WHEN an interactive element receives keyboard focus, THE Identity_Page_System SHALL display a visible focus indicator with a minimum 2px solid outline in the primary blue colour and a minimum 3:1 contrast ratio against adjacent colours.
5. THE Identity_Page_System SHALL mark required fields with `aria-required="true"`.
6. IF a field fails validation, THEN THE Identity_Page_System SHALL set `aria-invalid="true"` on that field and associate the corresponding error message with the field using `aria-describedby`.
7. WHEN a field that previously failed validation is corrected by the user, THE Identity_Page_System SHALL remove the `aria-invalid="true"` attribute from that field.
8. THE Identity_Page_System SHALL support full keyboard navigation across all identity page forms with a logical tab order that follows the visual layout sequence.
9. THE Identity_Page_System SHALL ensure all identity page forms are navigable and submittable without requiring a mouse.

### Requirement 8: SEO and Branding Consistency

**User Story:** As a product owner, I want all identity pages to have proper SEO meta tags and consistent branding, so that the pages appear professional in search results and social media previews.

#### Acceptance Criteria

1. THE Identity_Page_System SHALL include a `<title>` tag in the format "{PageTitle} - Portal" on every identity page, where PageTitle corresponds to the page name (e.g., "Register", "Confirm Account", "Forgot Password", "Reset Password") and the total title length does not exceed 60 characters.
2. THE Identity_Page_System SHALL include Open Graph meta tags on every identity page: `og:title` matching the page `<title>` value, `og:description` containing a description of 50 to 160 characters unique to that page, `og:type` set to "website", and `og:url` set to the absolute canonical URL of the page excluding query string parameters.
3. THE Identity_Page_System SHALL reference the shared Portal favicon via a `<link rel="icon">` element on every identity page.
4. THE Identity_Page_System SHALL include a `<meta name="description">` tag on every identity page with a unique description of 50 to 160 characters that describes the purpose of that specific page.
5. THE Identity_Page_System SHALL set `<meta name="robots" content="noindex">` on the Confirm Account and Reset Password pages to prevent indexing of token-bearing URLs.
